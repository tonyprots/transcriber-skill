# Handy → transcriber

[Handy](https://github.com/cjpais/Handy) вставляет диктовку сразу, но длинную
запись распознаёт плохо: вся запись уходит в модель одним вызовом, без нарезки
на окна. Эта интеграция оставляет Handy его быструю вставку и в фоне
прогоняет каждую запись длиннее 20 секунд через transcriber.

Как это устроено:

1. launchd-агент следит за папкой записей Handy (`WatchPaths`).
2. На новый `handy-*.wav` длиннее порога запускается `transcribe.py --mode max`
   с `--early-text`.
3. Как только готова основная модель, её читаемый текст без таймкодов уходит
   в буфер обмена и приходит уведомление. Проверяющую не ждём: на двухминутной
   диктовке это секунды вместо минуты.
4. Прогон досчитывается в фоне ради словаря терминов, полный набор файлов
   ложится в `<output-root>/<дата-время>-handy-<ts>/`, итоговый текст — рядом,
   в `<дата-время>-handy-<ts>.txt`.
5. Проверяющая меняет только названия: где она написала канон словаря, а
   основная модель — похожую ослышку («Bitrik4» → Битрикс24). Если итог
   отличается от быстрой версии и в буфере всё ещё она, буфер получает итог,
   и приходит второе уведомление. Скопированное поверх за время прогона
   не трогается.

Handy не меняется: ни настроек, ни форка.

## Агенту: текст по записи

```bash
python3 integrations/handy/handy_result.py "$HOME/Library/Application Support/com.pais.handy/recordings/handy-<ts>.wav"
```

Печатает пути и лучший готовый текст: пока прогон идёт — ранний, от основной
модели; когда полный набор готов — итоговый, со словарём и правками проверяющей
(transcriber перезаписывает файл текста). С `--full` ждёт полный набор и
печатает ещё названия, которые основная модель уронила, а проверяющая
услышала: в текст они не вставляются. Готов — сразу. Наблюдатель ещё
считает (рядом с результатом лежит `<дата-время>-handy-<ts>.running`
с его pid) — ждёт. Наблюдатель запись не взял (короче порога, упал, не
установлен) — сам запускает transcriber в ту же раскладку, кладёт текст в
буфер обмена, как наблюдатель, и выходит, проверка досчитывается в фоне. Пути берутся из plist агента.

Свой прогон рядом с идущим запускать нельзя: каталог результата скилл
создаёт только при сборке, оба прогона проходят раннюю проверку, второй
считает зря, отнимает CPU у первого и в конце падает на «Каталог уже
существует». 2026-10-02 так ушло полторы минуты при готовом тексте.

## Установка

```bash
integrations/handy/install.sh --output-root ~/transcripts/handy
```

Записи, которые уже лежат в папке Handy, отмечаются как виденные и
не обрабатываются. Флаги:

- `--min-seconds N` задаёт порог длительности, по умолчанию 20. Короче —
  одна-две фразы, Handy с ними справляется сам. Было 60, но 40-секундная
  диктовка с названиями (2026-10-03) так и осталась с текстом Handy.
- `--agent-python PATH` задаёт интерпретатор, который запускает сам агент.
  Если репозиторий лежит в `~/Documents`, `~/Desktop` или `~/Downloads`, macOS
  (TCC) не пустит туда `/usr/bin/python3`, запущенный launchd. Нужен бинарь,
  у которого этот доступ уже есть.
- `--uninstall` снимает агента.

Лог: `~/Library/Logs/ru.tonyprots.handy-transcriber.log`. Состояние (какие
записи уже виденные): `~/Library/Application Support/handy-transcriber/state.json`.

Упавшую запись (например, на нехватке места) агент повторяет при следующем
срабатывании, то есть на следующей диктовке: не больше трёх попыток, после
новых записей и без буфера обмена, чтобы старый текст не затёр свежий.

## Почему не через `external_script`

В Handy 0.9.6 есть способ вставки `external_script`: скрипт получает готовый
текст. В интерфейсе он есть только на Linux, но код ОС не проверяет. Этот путь
отвергнут, потому что Handy вызывает скрипт синхронно в главном потоке и на
время расшифровки завис бы целиком. Кроме того, скрипту пришлось бы самому
заниматься вставкой через буфер.
